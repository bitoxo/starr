# Contributing

Thanks for looking. Starr has one maintainer, so clear bug reports, well-described problems, testing against your own stack and review of the security-relevant parts help most.

- **Bugs** go to a [bug report](https://github.com/bitoxo/starr/issues/new?template=bug_report.yml), **ideas** to a [feature request](https://github.com/bitoxo/starr/issues/new?template=feature_request.yml): describe the problem, not only the fix. 👍 the requests you want too; I sort by them and label new ones within a week.
- **Questions** go to [Discussions › Q&A](https://github.com/bitoxo/starr/discussions/categories/q-a), **security problems** [privately](SECURITY.md), never to a public issue.
- **Code:** open an issue first for anything bigger than a bug fix. Larger features get a short written spec in the issue, which the maintainer accepts before code is written; new crates, core traits or large dependencies need agreement first. Tests first for logic and bug fixes, `just check` passes, one concern per pull request, [Conventional Commits](https://www.conventionalcommits.org/) title.
- **AI tools** are fine; Starr itself is built with Claude Code. Say in the pull request how you used them, and understand every line well enough to explain it in your own words. Unreviewed bulk output gets closed.

Development setup is in the [README](README.md#contributing). By contributing you agree that your contribution is licensed under [GPL-3.0-or-later](LICENSE).
